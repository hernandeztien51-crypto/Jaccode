# Fine-tune a 2B Qwen into jaccode's engine

The best route is to fine-tune **Qwen3.5-2B** (Apache 2.0, released March 2026) on compiler-verified Jac data and agent trajectories recorded in jaccode's own harness. Ship it as a **roughly 1.4 GB Q5_K_M GGUF** that jaccode loads in-process through **node-llama-cpp**: no API key, no per-token cost, nothing leaving the machine. Every step fits a single consumer GPU or a free Colab/Kaggle T4. Rented compute for the whole training programme should stay under about $100. The real costs are engineering time (an estimated 8 to 10 weeks for one person) and teacher-model API spend to generate verified data (an estimated $0.5k to $3k). The strongest feasibility evidence is from Jaseci Labs itself. A LoRA fine-tune of Qwen3-Coder-30B-A3B raised compile-and-run success on its Jac holdout from **10.5% to 74.7%** with only 5.5K to 8K training rows ([Jac_Model_Experiments](https://github.com/jaseci-labs/Jac_Model_Experiments)). Nobody has published the same result at 2B. My estimate for a well-trained 2B is about **20 to 35% greedy pass@1** on a Jac port of HumanEval and **80 to 95% type-check rate**, with dependable agent behaviour on short edit/check/fix loops but not on open-ended multi-file work. The four goals map onto the plan like this. Starting from a strong small base is the model choice. "Smarter" comes from verified SFT data, an optional reinforcement-learning stage with the Jac compiler as reward, and harness aids that are cheap to add. "Faster" and "small" come almost entirely from model size and quantization, not from fine-tuning. Plan around Jac's syntax churn: the language broke compatibility repeatedly between jaclang 0.16 and 0.40 in 2026, and jaccode itself still advertises `pip install jaclang` and "jac 0.8.x". Pin one compiler version before collecting a single training example.

## Qwen3.5-2B is the default; Qwen2.5-Coder-1.5B is the fallback

The base model sets the ceiling. Fine-tuning mostly teaches Jac's syntax and idioms, while algorithmic skill comes from the base model's Python ability, because Jac is a Python superset. Three candidates stand out in the 0.5B to 3B range as of November 2026. **Qwen3.5-2B** is the newest. It comes with a Base checkpoint, a 262K native context and an Apache 2.0 licence ([GIGAZINE](https://gigazine.net/gsc_news/en/20260303-qwen-3-5-small); [HF card](https://huggingface.co/Qwen/Qwen3.5-2B)). Among ≤2B models with official numbers it has the best agentic scores: **BFCL-V4 43.6 and TAU2-Bench 48.8**, ahead of the larger Qwen3-4B-2507 at 39.9 and 43.2. Its Artificial Analysis Intelligence Index is 16, against about 13 for Qwen3-1.7B ([Artificial Analysis](https://artificialanalysis.ai/articles/qwen3-5-small-models)). Its architecture also suits laptops: only 6 of its 24 layers use full attention and the rest are Gated DeltaNet linear-attention blocks ([HF card](https://huggingface.co/Qwen/Qwen3.5-2B)). By inference, its KV cache should be about a quarter of a plain transformer's, which matters when an agent keeps whole Jac files in context.

The main weakness: **Qwen has published no HumanEval, MBPP or LiveCodeBench numbers for the 0.8B or 2B sizes.** Its code quality is therefore an open question, and the first evaluation step has to answer it. That gap is why **Qwen2.5-Coder-1.5B** is the A/B baseline. It is older (November 2024) and weaker at agentic tool use, but it is a documented code specialist: **base HumanEval 43.9 and MBPP 69.2, instruct HumanEval 70.7** ([arXiv 2409.12186](https://arxiv.org/html/2409.12186)). It is a plain transformer that every tool supports, and it is Apache 2.0 ([Qwen blog](https://qwenlm.github.io/blog/qwen2.5-coder-family/)). The third candidate, **Gemma 4 E2B**, has the best published code score near 2B (**LiveCodeBench v6 44.0%**) and native function calling under Apache 2.0. However, it carries **5.1B parameters including per-layer embeddings** ([HF card](https://huggingface.co/google/gemma-4-E2B-it)), so its GGUF and RAM footprint will look more like a 4 to 5B model. That works against the "keep it small" goal.

Avoid three models that look attractive at first. **Qwen2.5-Coder-3B** has strong code scores (instruct HumanEval 84.1), but it is under the Qwen Research License, which is **non-commercial** ([LICENSE](https://huggingface.co/Qwen/Qwen2.5-Coder-3B/blob/main/LICENSE)). **LFM2.5** requires a paid licence once a company passes **US$10M in revenue**, and that obligation passes to downstream users ([Liquid AI](https://www.liquid.ai/lfm-license)). **Llama 3.2** derivatives must be named starting with "Llama" ([Meta](https://dev.meta.ai/llama/llama3_2/license)). All of these are a poor fit for a public npm CLI.

"Base" can mean two different starting checkpoints, and this decision matters. Qwen3.5-2B-Base ships its chat control tokens already trained "so that LoRA-style PEFT works with the official chat template" ([HF Base card](https://huggingface.co/Qwen/Qwen3.5-2B-Base)), so training from Base is viable. But the agentic scores above belong to the post-trained (instruct) model. A 2026 study of "no-resource" languages found that further pretraining gives the largest gains, that applying it to an instruct model damages instruction following, and that the fix is to pretrain the **base** model and then restore instruction following through weight-diff transfer from the instruct model ([arXiv 2606.16827](https://arxiv.org/abs/2606.16827)). I recommend running LoRA SFT on the **post-trained Qwen3.5-2B** as the default track, because it keeps its tool calling. Run "continued pretraining on Base, then instruct weight-diff, then SFT" as a parallel experiment, and adopt it only if it wins on the evaluation suite.

## Verified, idiomatic data matters more than volume

Public Jac looks plentiful but is narrow. The jaseci monorepo holds about **6,600 `.jac` files and 1.04M lines, all MIT-licensed** ([jaseci-labs/jaseci](https://github.com/jaseci-labs/jaseci)). By the research team's count on a 17 Nov 2026 clone, though, about 680K of those lines are the self-hosted compiler and runtime, and about 319K are compiler test fixtures, many deliberately invalid. Only about **38K lines of example apps, ~1,070 Jac code blocks in the docs, and 45 agent guides (~5.8K lines)** resemble the code a user would write. Raw scraping alone will not get there. Two further findings set the approach. First, **syntax drifted heavily during 2026**. Function-style `can`, `root()`, `&&`, `sv {}`/`cl {}` placement markers, `byllm` imports and inline `::py::` all became errors. Type checking now runs on every compile, including `jac run`, and `--no_typecheck` is gone ([breaking-changes.md](https://github.com/jaseci-labs/jaseci/blob/main/jac/jaclang/cli/docs/community/breaking-changes.md)). The in-repo release notes call **jaclang 0.40.0** the latest release, distributed as a standalone binary. PyPI's last release is 0.16.7 from June 2026 ([PyPI](https://pypi.org/project/jaclang/); [install guide](https://github.com/jaseci-labs/jaseci/blob/main/jac/jaclang/cli/docs/quick-guide/install.md)). Second, **Jaseci Labs' own training sets were built against jaclang 0.16.1** ([Jac_Model_Experiments](https://github.com/jaseci-labs/Jac_Model_Experiments)). Any data reused from them, or scraped from the web, has to be re-validated with the pinned current compiler. jaccode needs this fix too: `src/prompt.ts` and `src/tools/shell.ts` still tell users to `pip install jaclang`, which installs the stale 0.16 line.

The best-evidenced way to create more data is **MultiPL-T**. A strong model translates Python functions *and their tests* into the target language, and only translations that pass are kept. That funnel produced 37K to 48K validated items per language and lifted a 1B model's OCaml pass@1 **from 1.5 to 9.7**. Training on natural in-language code from The Stack, by contrast, "barely increases" performance and sometimes hurts it ([arXiv 2308.09895](https://arxiv.org/html/2308.09895v6)). JetBrains' Kotlin work agrees. On CodeLlama-7B, **15K translated exercises (+16 pass@1) beat 25K curated files (+12), which beat 4M raw files (+3)** ([arXiv 2405.19250](https://arxiv.org/html/2405.19250)). Python translation never produces Jac's distinctive features: nodes, edges, walkers, `visit`/`report`, `by llm()`, `impl` annexes. So translation should be paired with **OSS-Instruct-style generation**: prompt a strong model with real Jac snippets from the examples, docs and guides, and ask for new tasks and solutions in the same idiom ([Magicoder, arXiv 2312.02120](https://arxiv.org/abs/2312.02120)). Add Evol-Instruct to vary difficulty ([arXiv 2306.08568](https://arxiv.org/abs/2306.08568)). The breaking-changes table can be turned directly into "migrate this legacy Jac" pairs, which is useful because users will paste old code. Gate every sample on the pinned compiler: `jac check` exit 0, plus `jac test` or a `with entry` assertion harness where tests exist.

Jaseci's own experiments warn that more rows can hurt. Their 14,792-row merged corpus (exp08) scored lowest of the late runs at **70.5%**, while the 5,474-row exp06 reached **74.4%**. Graph-native code made up only 15.7% of exp08, and the authors concluded that "data mix and fit to the eval surface mattered more than row count" ([HISTORY.md](https://raw.githubusercontent.com/jaseci-labs/Jac_Model_Experiments/main/docs/HISTORY.md)). Budget the mix deliberately. My estimate for a 2B model, extrapolated from the MultiPL-T, Kotlin and Jaseci ranges rather than measured, is **10K to 25K verified code samples**. Cap translated-function rows at roughly half. Guarantee meaningful shares of walker/OSP code, `by llm()` code, app-level code, and migration/fix tasks. Replay **15 to 30% general Python and chat data** to limit forgetting. Smaller models probably need the top of that range and more epochs; MultiPL-T trained its 1B for 7 epochs.

The agent half of the dataset follows **SWE-smith**. Synthesize verifiable broken-code tasks cheaply, roll out a strong teacher agent, keep only successful trajectories (at most 3 per task), and fine-tune on those. In that work, **about 2K trajectories took a 7B model to 15.2% on SWE-bench Verified**, and 500 already helped a 32B model ([arXiv 2504.21798](https://arxiv.org/html/2504.21798)). For Jac, break valid programs in four ways: procedural mutations, LM-introduced bugs, legacy-syntax injection (`can` functions, `root()`, `&&`), and type errors. Add feature requests such as "add a walker that counts reachable nodes, with a test". jaccode can produce these trajectories itself, which is a structural advantage. Its Anthropic provider already runs the exact tools the small model will use (`read_file`, `edit_file`, `multi_edit`, `grep`, `glob`, `bash`, `jac`, `todo_write` in `src/tools/`), so teacher rollouts recorded through jaccode carry identical tool names and schemas. Convert them to OpenAI-style `messages` + `tools` JSONL, render them through Qwen3.5's own chat template, and mask the loss so the model learns only assistant and tool-call tokens, never tool outputs ([NeMo AutoModel agent SFT](https://docs.nvidia.com/nemo/automodel/latest/recipes-e2e-examples/agent-sft)). Jac edit/check loops are much shorter than SWE-bench tasks, so I estimate **1K to 5K trajectories** is enough. Do not train on the `jac mcp` tool names unless jaccode adopts them.

## One consumer GPU covers SFT; reinforcement learning is the expensive, optional stage

Use **Unsloth wrapping TRL's trainers**. It explicitly supports Qwen3.5 from 0.8B to 9B. bf16 LoRA needs about **5 GB of VRAM at 2B** (3 GB at 0.8B, 10 GB at 4B), and it exports a GGUF in one call with `save_pretrained_gguf` ([Unsloth Qwen3.5 guide](https://unsloth.ai/docs/models/qwen3.5/fine-tune)). Two Qwen3.5-specific cautions conflict with generic small-model advice. Unsloth **advises against QLoRA for Qwen3.5** "because of higher-than-normal quantization differences", and Qwen3.5 needs **Transformers v5**, with custom kernels that compile slowly on a T4. Because bf16 LoRA at 2B fits in 5 GB, a 16 GB T4 runs the correct configuration, and QLoRA is not needed. On Kaggle, choose **2x T4, not the P100**: the P100 is CUDA capability 6.0, below Unsloth's 7.0 minimum ([Unsloth requirements](https://unsloth.ai/docs/get-started/fine-tuning-for-beginners/unsloth-requirements)). torchtune is no longer maintained ([README](https://raw.githubusercontent.com/meta-pytorch/torchtune/main/README.md)), so do not use it.

For SFT, start from Unsloth's recommended settings: **rank 16 to 32, alpha equal to rank or 2x rank, learning rate 2e-4, 1 to 3 epochs, effective batch 16, all seven linear projections, responses-only loss**. Treat training loss below 0.2 as a sign of overfitting ([Unsloth LoRA guide](https://unsloth.ai/docs/get-started/fine-tuning-llms-guide/lora-hyperparameters-guide)). LoRA has a measured trade-off: on code it **learns less than full fine-tuning but forgets less** ([arXiv 2405.09673](https://arxiv.org/html/2405.09673v2)). Forgetting is what kills general Python and tool-calling skill, so LoRA is the right default. Full fine-tuning of a 2B model in bf16 fits a 24 GB card by rough estimate, and is the escalation path if evals show LoRA underfitting Jac syntax. Continued pretraining on raw Jac is the more speculative lever. The corpus is only about 10M tokens (estimate), and much of it is compiler internals. If you try it, follow Unsloth's CPT recipe: add `embed_tokens` and `lm_head` with a 2 to 10x lower learning rate ([Unsloth CPT](https://unsloth.ai/docs/basics/continued-pretraining)), on Base only.

Reinforcement learning with the compiler as reward is the main way to make the model "smarter" beyond what a teacher can show it. It is also where small models are least predictable. The strongest result is **Agnostics**: GRPO with a binary all-tests-pass reward raised Qwen3-4B's Fortran pass@1 **from 0 to 15%**. SFT on 1,987 frontier-model Fortran solutions (about $96 of generation) reached only 2 to 3% ([arXiv 2508.04865](https://arxiv.org/html/2508.04865v2)). In the same study, **Qwen3-1.7B did not improve** on the harder problem set, and partial-credit rewards were dropped because models exploited them. A May 2026 run with Qwen2.5-Coder-1.5B and TRL GRPO on one 48 GB card raised compilable OCaml output **from about 2 in 10 to about 7 in 10**. It also showed reward hacking (marker spam, chatty apologies scoring like broken code), a graduated reward that settled into "consistent mediocrity", and a best checkpoint that came before the final step ([nilenso](https://blog.nilenso.com/blog/2026/05/18/training-a-small-model-to-write-better-ocaml-with-rlvr-and-grpo/)). A student report found no gain at all from a compiler-oracle reward at 1.5B ([CS224R](https://cs224r.stanford.edu/projects/pdfs/Monami%20Dutta%20Gupta%20submission_416208168/CS224R_Project_Final_Report.pdf)). Run GRPO only after SFT, on problems the SFT model solves 10 to 70% of the time. The main reward is **1 when `jac check` and the hidden tests pass**, plus a small compile bonus that is removed once pass rates rise, and penalties for non-code output. Track reward variance within each group as the health signal. TRL's GRPOTrainer accepts plain Python reward functions and defaults to 8 generations, no KL term and LR 1e-6 ([TRL docs](https://huggingface.co/docs/trl/main/en/grpo_trainer)). Unsloth reports 1.5B GRPO in about 5 GB of VRAM ([Unsloth GRPO](https://unsloth.ai/blog/grpo)). DPO on "idiomatic vs transpile-shaped" pairs, which Jaseci already tried, is a cheaper offline complement.

## Gate every stage on compile rate, pass@1 and edit-application rate

Small models fail in ways that one headline number hides, so build the evaluation first and baseline every candidate model on it before training. The function-level layer follows **MultiPL-E**: translate HumanEval (164) and sanitized MBPP (~400) into Jac signatures, docstrings and hidden tests, then score greedy pass@1 by execution ([arXiv 2208.08227](https://arxiv.org/abs/2208.08227)). Jaseci Labs already has a **164-task Jac HumanEval port in JaseciBench**, but its grading tests sit in a private vault and it pins Jac 0.34.8 ([JaseciBench](https://github.com/jaseci-labs/JaseciBench)). Ask the maintainers for access so results are comparable, and keep an open local dev copy for fast iteration. Copy CangjieBench's quality control: check each reference solution against deliberately broken variants so the tests reject common wrong answers ([arXiv 2603.14501](https://arxiv.org/html/2603.14501v2)). Report **parse rate, type-check rate and pass@1** side by side. On an unseen language, CangjieBench found compile rate and pass@1 within about 3 points of each other, and "foreign syntax" behind **82 to 84% of failures**. Add 50 to 150 Jac-specific tasks on walkers, nodes/edges, `by llm()` and `impl`, because HumanEval ports can be passed with Python-flavoured Jac. Decontaminate training data against all of it.

The agent layer should run **jaccode's own loop**. Its mock and Ollama providers (and later the in-process provider) exercise the real tool schemas and prompts. Measure five things from logs. **Tool-call validity:** does the call parse against the zod schema? **Edit-application rate:** `edit_file` already raises distinct "not found" and "occurs N times" errors in `src/tools/files.ts`, so the split is free. **Turns-to-green** on seeded broken files graded by `jac check` and hidden `jac test`. **Resolve rate** on 10 to 20 multi-step repo tasks across two or three small Jac apps. **A process-failure taxonomy:** identical-retry loops, editing without reading, never running `jac check`, context overflow. Use 3 seeds per task, because small-model agent runs vary a lot. Regression-test Python HumanEval/MBPP after every stage to catch forgetting. Always evaluate the **exported GGUF under llama.cpp**, not just the HF checkpoint: Unsloth notes that most "bad output after export" reports come from chat-template or EOS mismatches ([Unsloth GGUF docs](https://unsloth.ai/docs/basics/inference-and-deployment/saving-to-gguf)).

Measure harness aids as on/off ablations too, because for a small model some of them may be worth as much as training. On an unseen language, a compact syntax reference in the prompt raised GPT-5's pass@1 **from 4.8% to 50.4%** and cut foreign-syntax failures from about 84% to about 30%. Retrieval over docs helped less, and pass@10 with the syntax reference beat single agent runs on every backbone ([CangjieBench](https://arxiv.org/html/2603.14501v2)). Type-constrained decoding "reduces compilation errors by more than half" ([arXiv 2504.09246](https://arxiv.org/abs/2504.09246)). In order of payoff per effort, the cheap wins for jaccode are: an automatic `jac check` after every edit with errors fed back; a short current-syntax cheat sheet in the system prompt, drawn from `jac-essentials`; and JSON-schema-constrained tool calls. For function-level requests, sampling k candidates and keeping the first that passes `jac check` may beat a multi-turn loop.

## A 1.4 GB GGUF and node-llama-cpp put the model inside the CLI

The shipping path is mature. Merge the LoRA adapter, convert with llama.cpp's `convert_hf_to_gguf.py` to BF16, and run `llama-quantize` with an **importance matrix computed on Jac and Python samples** "to minimize accuracy loss" ([llama.cpp quantize README](https://github.com/ggml-org/llama.cpp/blob/master/tools/quantize/README.md)). Unsloth can do the export in one call. For Qwen3.5-2B, the measured sizes are **Q4_K_M 1.28 GB, Q5_K_M 1.44 GB, Q6_K 1.57 GB, Q8_0 2.01 GB** ([unsloth/Qwen3.5-2B-GGUF](https://huggingface.co/unsloth/Qwen3.5-2B-GGUF/tree/main)). The fact that these files exist also shows llama.cpp supports the hybrid architecture. Practitioners argue that 1 to 3B models lose proportionally more at 4 bits ([tinyweights.dev](https://tinyweights.dev/posts/gguf-quantization-levels-q4-q5-q8/)). A 2026 study found 4-bit KL divergence stays small down to Llama 1B, while 3-bit degrades sharply at small sizes ([arXiv 2607.10855](https://arxiv.org/pdf/2607.10855)). Nobody has measured this for Qwen3.5-2B. Default to **Q5_K_M**, publish Q4_K_M and Q8_0 in the same Hugging Face repo, and choose the default only after running `llama-perplexity --kl-divergence` and the Jac eval on each quant. Note that the quant also sets speed: CPU decoding is memory-bandwidth bound, so in llama.cpp's own table **Q4_K_M generates about 40% faster than Q8_0** (71.9 vs 50.9 tok/s on an 8B model).

**node-llama-cpp 3.22.3** (MIT, published 5 Nov 2026, Node ≥20, ESM-only, ~455K weekly downloads) fits jaccode, which is already ESM on Node 20+ ([npm](https://registry.npmjs.org/node-llama-cpp)). It ships prebuilt binaries for macOS (Metal), Linux and Windows (CPU, CUDA, Vulkan). `resolveModelFile("hf:<org>/<repo>:Q5_K_M", dir)` downloads on first use and resolves offline afterwards ([downloading models](https://node-llama-cpp.withcat.ai/guide/downloading-models)). It also supports JSON-schema grammars and `defineChatSessionFunction` function calling ([function calling](https://node-llama-cpp.withcat.ai/guide/function-calling)). Integration means a new `src/providers/local.ts` modelled on the existing `OllamaProvider`. It would feed jaccode's tool specs, which `tool.ts` already converts from zod to JSON Schema, into grammar-constrained calls so the model cannot emit a malformed tool call. One schema detail: node-llama-cpp treats all function parameters as required, so optional fields such as `edit_file`'s `replace_all` need a `oneOf`-with-null encoding. There are two packaging traps. First, npm may install the **209 MB CUDA and 76 MB Vulkan** binary packages alongside the 34 MB CPU one, so make node-llama-cpp an optional or lazily installed dependency, or pin the platform packages. Second, whether node-llama-cpp auto-detects Qwen3.5's `<tool_call>` template is unverified. Test it with `npx node-llama-cpp chat`, and fall back to a `JinjaTemplateChatWrapper` built from the exact template used in training. transformers.js 4.3.2 is the alternative runtime, but its support for the Qwen3.5 hybrid in ONNX and for k-quants is unproven.

Speed figures for this size class come only from secondary sources, which put a 1.5 to 2B Q4 model at **roughly 25 to 40 tokens/s on a laptop CPU** and a 3B at 12 to 20 ([InsiderLLM](https://insiderllm.com/guides/cpu-only-llms-what-actually-works/); [promptquorum](https://www.promptquorum.com/local-llms/best-cpu-only-llm)). My estimate for resident memory is about **2 to 2.5 GB** at 8 to 16K context. The bigger CPU latency cost is prefill: reading a long system prompt plus Jac files before the first token appears. Keep jaccode's prompt and tool outputs short for the local model, and measure with `llama-bench` on real target laptops. Compared with the 30B-class `qwen3-coder` that jaccode's README currently suggests for Ollama, the 2B is roughly a tenth of the download (my estimate). It needs no separate server and runs comfortably on machines without a GPU.

These estimates rest on three anchors. The fine-tuned model's Python ability caps it: Qwen2.5-Coder-1.5B scores 43.9 base HumanEval. Jac's closeness to Python should make its gap mostly a matter of syntax, which fine-tuning fixes well. And MultiPL-T's 1B ceiling of 10 to 17% came from a much weaker 2023 base model. For agent work the evidence is sobering. 1 to 3B models top out around **65% BFCL overall and 55% multi-turn** even after optimization ([arXiv 2511.22138](https://arxiv.org/abs/2511.22138)). A pre-registered study found **0 of 16 off-the-shelf Qwen3 configurations (0.6B to 8B)** eligible for agent microtasks ([arXiv 2610.00025](https://arxiv.org/abs/2610.00025)). Fine-tuning on jaccode's own trajectories and constraining tool calls with a grammar are meant to close exactly that gap, but no published result shows a 2B closing it. The realistic product is a free, private, offline model that writes and fixes Jac reliably in short, compiler-checked loops. Claude stays one flag away for hard multi-file tasks.

Two conflicts in the source material are worth flagging. The Jac CLI reference page still describes `jac ai` with local-model support ([docs](https://docs.jaseci.org/reference/cli/)), but the breaking-changes log says `jac ai` was removed in favour of `jac mcp` plus guides ([breaking-changes.md](https://github.com/jaseci-labs/jaseci/blob/main/jac/jaclang/cli/docs/community/breaking-changes.md)). The changelog is the more recent and specific source, so trust it. Also, the jaccode README's "jac 0.8.x" and JaseciBench's pinned 0.34.8 both trail the in-repo 0.40.0. Settle on one version in Phase 0.

## Conclusion

The project is less risky in its training than in its data. Fine-tuning a 2B model costs pocket change, and every tool in the chain (Unsloth, TRL, llama.cpp, node-llama-cpp) handles Qwen3.5 today. What decides the outcome is whether the data is current-syntax, compiler-verified, idiomatic Jac in a deliberate mix. Jaseci's own experiments already show that adding more rows can make the model worse. jaccode has an unusual advantage: the harness the small model will run in can also generate its training trajectories with a frontier teacher, so the tool schemas, prompts and edit semantics match exactly with no translation layer. That makes jaccode its own data engine. Once the local model ships, opt-in logs of failed loops become the next round's training tasks.

Treat "smarter", "faster" and "smaller" as separate levers. Size and quantization buy speed and footprint, and no amount of training changes tokens per second. Verified SFT data buys syntax correctness. RL and harness aids (auto-check, cheat sheet, constrained tool calls, sample-and-verify) buy the remaining reliability, and some of the harness aids help the existing Ollama path before any training happens. Build the evaluation and those aids first. They give the earliest measurable improvement, and they set the bar that the fine-tuned 2B has to clear to justify being shipped.
